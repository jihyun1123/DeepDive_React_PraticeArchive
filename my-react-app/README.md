```
나의 예측:
1. 렌더링 시작, count : 0
3. 렌더링 끝
2. effect 실행, count : 0
```

**Q2. 버튼 클릭 후(update) 출력 순서는?**

```
나의 예측:

```

### 정답 확인 후 생각해볼 것

    -> React가 UI를 설계 후 그린 뒤, 사이드 이펙트를 실행하기 위해서 

- 왜 이런 순서로 실행될까요?
    -> React는 화면을 그리는 일을 최우선으로 하고, 그 다음에 사이드 이펙트를 처리하기 때문

## 실습 2 : 의존성 배열 3가지 패턴 비교
### 실험 기록

| 버전 | 첫 렌더링 | count +1 버튼 5번 | name 변경 버튼 1번 | 총 실행 횟수 |
| --- | --- | --- | --- | --- |
| A (생략) | 1 회 | 5 회 | 1 회 | 7 회 |
| B ([]) | 1 회 | 0 회 | 0 회 | 1 회 |
| C ([count]) | 1 회 | 5 회 | 0 회 | 6 회 |

### 생각해볼 것

- 버전 A는 왜 name 변경에도 반응할까요?
    - deps 생략 = 모든 렌더링 후 실행됨
        - state가 뭐든 하나라도 바뀌면 리렌더링 -> effect 실행됨
        => deps가 없어서 모든 렌더링 후 실행되기 때문


- 버전 B는 왜 버튼을 아무리 눌러도 1번만 실행될까요?
    - [ ] : 처음 한 번만 실행됨
        - 이후 state가 아무리 바뀌어도 effect는 무시함
            => 의존성이 없다고 명시했기 때문에 mount 전용 effect


- 버전 C는 왜 name 변경에는 반응하지 않을까요?
    - effect는 deps에 있는 값만 감시하기 때문에, count가 바뀌었을 때만 다시 실행
        - name이 바뀌어도 count가 그대로면 effect를 실행 X
            => deps 배열에 name이 없어서 변경을 감시하지 않음

## 실습 3 : cleanup 실행 시점 확인
### 예측해보기

**Q1. 버튼을 0→1→2→3 으로 3번 클릭하면 콘솔에 어떤 순서로 출력될까요?**

```
나의 예측 (순서대로 작성):
1. effect 실행, count: 0
2. cleanup 실행, count : 0
3. effect 실행, count: 1
4. cleanup 실행, count : 1
5. effect 실행, count: 2
6. cleanup 실행, count : 2
7. effect 실행, count: 3
```

### 핵심 질문

- cleanup의 count 값은 **이전 값**인가요, **현재 값**인가요?
    - 이전 값
        why? cleanup은 이전 effect에 딸려 있던 함수로, 이전 렌더 당시의 state를 기억(클로저)하고 있음

- cleanup이 먼저 실행되나요, 새 effect가 먼저 실행되나요?
    - cleanup이 먼저 실행된다
        - React 철학 : 새 effect를 실행하기 전에, 이전 effect가 남긴 흔적부터 정리하자 !

## 실습 4 : Stale Closure 직접 체험

### 과제 A: 문제 재현
아래 코드를 실행하고 3초 동안 기다려보세요. count가 어떻게 되나요?

**Q1. 예상: 3초 후 count는 얼마일까요?**

- 예상: count : 3
- 실제: count : 1

### 과제 B: 문제 해결

`setCount(count + 1)`을 **functional update** 방식으로 수정해보세요.

```
setCount(prev => prev + 1);  // 🟢 수정
```

**Q2. 수정 후 3초 뒤 count는 얼마인가요?**

- 실제: 3


### 생각해볼 것

- 왜 `count + 1`은 항상 1이 되었을까요?
    - 첫 렌더링 때 count = 0
    - useEffect([]) 실행, 이 시점의 count(0)를 클로저로 캡처
    - 그 이후 interval은 계속 같은 count(0)만 바라봄
        => effect 안의 함수는 effect가 실행되던 시점의 state를 기억한다
        이때 deps가 []라면 최신 값으로 갱신되지 않음
            왜냐하면 빈 배열은 최초 렌더링 1번만 실행되기 때문

- `prev => prev + 1`은 왜 제대로 동작할까요?
    - React가 가장 최신 state를 prev로 전달하기 때문에, 클로저랑 상관 없음
    - 그래서 deps가 []이어도 안전함
        => 현재 시점의 최신 state를 보장해서 넘겨주기 때문

## 실습 5 : StrictMode 2번 실행 확인

### 과제 A: cleanup 없는 버전
**Q1. 첫 렌더링 시 "타이머 시작!"이 몇 번 출력되나요?**

- 예상: 1번
- 실제: 2번
    => mount -> unmount -> mount를 일부러 한 번 더 시킴
        그래서 effect가 두 번 실행 됨

**Q2. count가 1초에 몇씩 증가하나요?**

- 예상: +1
- 실제: +2

### 과제 B: cleanup 추가
**Q3. cleanup 추가 후 "타이머 시작!"과 "타이머 정리!"가 각각 몇 번 출력되나요?**

- 타이머 시작: 2번
- 타이머 정리: 1번

1️⃣ mount → effect 실행 (타이머 시작)
2️⃣ StrictMode 강제 unmount → cleanup 실행 (타이머 정리)
3️⃣ 다시 mount → effect 실행 (타이머 시작)

**Q4. count가 1초에 몇씩 증가하나요?**

- 실제: +1

### 생각해볼 것

- StrictMode는 왜 일부러 2번 실행할까요?
    - React 의도 : 이 effect가 정말 안전한가?
    => 문제 있는 effectㄹ르 개발 단계에서 터뜨리기 위하여 2번 실행함

- cleanup이 없으면 왜 타이머가 2개가 되나요?
    - StrictMode가 effect 실행, 바로 unmount 시도
        - 하지만 cleanup이 없으면 이전 타이머가 살아있기 때문에
            타이머 1개 + 타이머 1개 = 2개

🧠 StrictMode 한 문장 정리
StrictMode는 개발 모드에서
effect의 안전성을 검증하기 위해
일부러 mount → unmount → mount를 반복한다
